# Meepo AI 开发约定

开始工作时读取本文件和相关源码、Javadoc、测试及文档。本文中的代码路径以仓库根目录为基准，Markdown 链接以本文位置为基准。当前任务的明确要求优先于项目偏好，已有设计可以随需求调整。

## 项目定位与版本

Meepo 是以字符为核心的轻量模板引擎，指令借用目标语言的注释，正文保留可读的示例值，便于使用原有的语法高亮、编辑和预览能力。
常用场景是邮件、配置文件和简单文本生成。核心模板处理由项目自身实现，现有生产依赖为 JetBrains annotations 和 SLF4J。

当前开发版本为 **2.0.0-SNAPSHOT**，正式版目标为 **2.0.0**，发布坐标为 `pro.fessional:meepo:2.0.0`。
POM 默认保留 `-SNAPSHOT`，正式发布由匹配的 tag 通过 `-Drevision` 覆盖本次构建版本。版本、依赖及 Maven profiles 以 `pom.xml` 为准。
生产代码兼容 **Java 8**，使用 Maven、JUnit 5、JaCoCo 和 JMH。较新 JDK 的测试源目录由 POM 按运行版本启用。

决策顺序为正确性、可读性、性能及分配成本。兼容性、线程安全和资源所有权需要随行为一起核实。

## 人工与 AI 协作

- 每轮修改须明确独立可验证的目标、范围和验收方式，变更粒度以人工能够理解并逐项审核为准。
- AI 需说明修改意图、实现和验证结果。每轮完成后以独立 commit 收口，使人工能够通过该 commit 的 diff 识别并审核本轮变更。
- **一旦出现人工无法理解或审核的修改，即认为项目失控。** 此时先停止扩大变更，拆分并解释已有修改，直到人工能够完成审核。

## 工作方式

- 默认中文交流。Java 源码的 Javadoc 和行内注释使用简洁英文，解释用途、意图、边界和取舍。
- 先检查 `git status`、当前分支和相关 diff，保留用户手工修改。Git 提交、分支调整及远程操作按本次任务的授权执行。
- 按真实调用调查设计。检查公开入口、内部调用、历史数据及测试，再判断复制、缓存、反射或短路是否必要。
- 对授权范围内的读取、修改、构建和验证持续执行，遇到实际阻碍说明具体原因。工具权限以当前运行环境为准。
- 保持可逐项 review 的小范围 diff。依赖升级、公开 API 扩充和额外工具层需要有当前任务或测量证据支持。

## 语法与架构

- 修改语法先读 [语法规范](syntax.zh.md)，修改类型职责先读 [命名说明](naming.zh.md)。同步核对 Parser、Gene、Holder 及相关调用。
- DNA 在解析时处理，RNA 在每次 merge 时执行。替换位置在 parse 阶段确定，替换文本按原文输出。
- 输入字符集属于字节解码边界，输出字符集属于字节编码边界。默认 UTF-8，HI-MEEPO 声明注释边界，解析节点持有字符文本。
- Writer 的编码由调用方构造的 Writer 决定，OutputStream 的编码由 merge 参数决定。调用方负责其输出流的 flush 和 close。
- Gene 可复用。每次渲染的变量、分支、循环状态、可变引擎和编码器按本次调用隔离。共享缓存发布完整、一致的快照。
- Utxt 的字符和内部缓存字节按只读约定使用。检查公开返回值的所有权及真实外部调用，按需要决定复制或共享。
- EACH 的有限游标先收集后遍历，保持 total、count、步长及反向索引的一致语义。输入 Stream 的生命周期由调用方管理。
- 沿用 Meepo 的类名、包名及方法风格。输出入口使用 `merge` 重载，公开 API 的增改需检查本次需求和兼容影响。

## Java 与格式化

- 用真实 JDK 8 编译生产源码。仅设置 source/target 为 8 无法验证新 JDK API 的兼容性。
- 复用现有 JDK 类型、项目工具和表达式实现。性能问题先测量，再决定是否增加缓存、池、包装类型或抽象层。
- 保留短路求值和有意义的局部变量。身份哨兵、Class、枚举及约定的引用比较需要按其身份语义处理。
- 检查 null、空值、数组、集合、引用共享、异常、资源关闭及部分输出。线程内状态和可回收缓存需要有明确生命周期。
- Java 格式参考 `../professional-wings/wings/wings-idea-style.xml`。本机有 IDEA formatter 时用该配置处理修改的 Java 文件，并检查格式化 diff。
- 格式化工具不可用时按相邻代码风格修改，并在交付中说明格式化验证情况。

## 测试与覆盖率

- 类级用例与生产类同名，使用对应包下的 `ClassNameTest`。跨类协作、安全边界和集成场景按实际职责组织。
- 通用测试在 `src/test/java`，JDK 8 运行时用例在 `src/test/jdk8`，Java 17+ 用例在 `src/test/jdk17`。
- 按行为选择边界数据，尤其检查空输入、缺失值、极值、Unicode、字符集、片段边界、有限游标、异常及资源所有权。
- 缺陷修复增加能让旧实现失败的断言。并发测试使用 barrier、latch、受控 executor 和超时，验证输出及状态隔离。
- 生产行为修改以类、方法、行、分支和指令覆盖率 100% 为验收目标，同时检查报告中的复杂度。使用新鲜执行数据，核对 Surefire 的测试数、失败数和跳过数。
- 真实 JDK 或环境才能覆盖的分支在相应条件下验证。合并 JaCoCo 数据时使用同一编译产物，说明各次与合并结果。
- 纯文档修改验证示例和链接。构建、依赖和发布配置修改需要验证实际构建、测试及制品。

```sh
./mvnw -B -ntp verify
./mvnw -B -ntp -Pcoverage verify
./mvnw -B -ntp -Pcoverage -Dtest=ClassNameTest test
```

依赖完整时可以加 `-o`。本地保留用户的测试和性能产物，需要干净构建时使用独立临时目录。
CI 验证 Java 8、11、17、21，发布构建使用 Java 8。Maven 版本统一由 `.mvn/wrapper/maven-wrapper.properties` 固定，使用 `./mvnw` 或 `mvnw.cmd`。mise 管理本机 JDK。

## 性能验证

- JMH 代码统一放在 test 的 `pro.fessional.meepo.jmh` 包中，比较引擎及基准依赖使用 test scope。
- 按 [JMH Prompt](prompt/jmh.prompt.zh.md) 核对所有引擎的字符与字节结果，再测量 parse、merge、分配和共享模板场景。
- 记录 JDK、引擎版本、负载、输出类型、线程、fork、预热、测量与误差。吞吐 ops/s 越高越好，耗时和 B/op 越低越好。
- 相对比较以 Meepo 为 100%，按指标方向换算，优者高于 100%。说明零基准、误差和统计口径。
- 原始测量数据及分析文件使用临时目录，汇总有效结论进入性能文档。构建产物及执行结果使用忽略的 `target/`。

## 文档与发布

- 项目根目录、工程元数据和脚本默认使用英文，默认英文 Markdown 文件使用 `.md`。中文译本使用 `.zh.md`，例如 `readme.zh.md`。
- `doc/` 默认编写中文，中文 Markdown 文件统一以 `.zh.md` 结尾。其他语言按对应语言后缀组织。
- 根目录 `AGENTS.md` 是英文自动发现入口，完整开发约定位于 `doc/AGENTS.zh.md`，两者通过链接衔接。

- 文档目录使用单数 `doc/`。当前规则和结论放在文档正文，按日期组织的迭代与差异放在 `doc/changelog/`，执行提示放在 `doc/prompt/`。
- 实用模板放在 `doc/example/`，以邮件、配置文件等小场景解释模板、输入及输出。示例使用原生扩展名，修改后实际渲染校验。
- 保留两个 README 的外部详细文档入口。外部中文用户文档位于同级 Wings 的 `observe/docs/src/zh/b-meepo`，修改范围按当前任务确定。
- 当前发布流程见 [Maven 发布](release.zh.md)。Central 正式版使用 `sign,central`，SNAPSHOT 使用 `central`。私服由用户在本地传入 `altDeploymentRepository` 或使用 `altrh`，凭证由用户本地 Maven settings 和环境变量提供，按需要叠加 `sign`。发布脚本统一放在 `.github/script/`。发布版本由 POM 和发布种类派生，正式 tag 与去掉 `-SNAPSHOT` 的 POM 版本一致。
- 发布、打 tag 和推送需具有当前任务授权。报告中区分本地构建、签名包演练、Actions 执行和 Central 实际发布结果。
- 交付说明实际变更、已完成验证、配置选择及尚待用户提供的外部凭证或权限。
