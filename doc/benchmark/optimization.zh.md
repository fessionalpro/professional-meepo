# Meepo 性能设计与比较结论

可执行基准位于 `src/test/java/pro/fessional/meepo/jmh` 与 `src/test/jdk17/pro/fessional/meepo/jmh`。
依赖统一由根 POM 的 `test` scope 管理；每次测量按 [JMH Prompt](../prompt/jmh.prompt.md) 重新执行。

## 执行与缓存设计

- `Cmap` 叠加本次变量与共享的函数快照，避免每次渲染复制全部默认函数；完整 Map 视图按需在已有变量表中展开。
- `Cbuf` 使用 StringBuilder 批量追加字符和基本类型，减少小结果的缓冲分配。
- 默认容量根据模板大小估算，并参考实际结果调整；显式容量重载可用于固定条件的比较。
- `Utxt.getBytes` 直接编码固定字符数组，并可复用最近一次编码快照。`Ubuf` 对 UTF-8、GBK 等已知无状态编码复用片段字节，并合并跨片段代理对。
  其他编码使用连续编码器保留 BOM 和状态。每片段只软缓存最近一种编码及其字符集，切换或回收后按需重建。
- `Ubuf` 通过 CharsetEncoder 直接读取 char[] 和字符串切片的 CharBuffer 视图，复用字节缓冲区。
  完整 String 在已知无状态编码下使用 JDK 编码快路径。固定片段通过 Dent.write(Writer, Utxt) 分派输出。
  固定片段编码使用 Charset.encode 和原 char[] 的 CharBuffer 视图，省去中间 String 的字符复制。有效字节未占满容量时裁剪一次字节数组。
- 字节输出统一使用 `merge(ctx, OutputStream[, Charset])`；数组收集适配器放在测试中。
- `Meepo.steam` 转交本次独占的输出缓冲区，省去生成返回流前的最后一次数组复制。
- Parser/Holder 将已完成的节点列表交给 Gene，公开构造器仍建立调用方集合快照；辅助类型的所有权与线程约束见 [命名与执行流程](../naming.zh.md)。
- 属性访问缓存只保存类型与成员绑定，不保存请求值；函数别名和导航计划在解析阶段准备。
- WHEN 保留短路，未选中的分支不重复执行表达式；循环状态位于每次创建的 Acid。

## 测量条件

本节汇总 2026-11-13 的测量结果，比较 POM 固定版本的正式发布依赖。版本与口径调整见 [测量记录](../changelog/2026-11-13-benchmark.zh.md)。

| 项目 | 条件 |
|:--|:--|
| 机器 | Apple M5，10 核，32 GB，macOS 27.0.1 |
| JVM | Temurin OpenJDK 21.0.10+7-LTS，64-Bit Server VM |
| JMH | 1.37，compiler blackhole |
| 堆 | 每个 JVM 使用 `-Xms256m -Xmx256m` |
| 热渲染 | 每组 2 个独立 fork，每个 fork 预热 3 × 1 秒、测量 5 × 1 秒 |
| 输出门槛 | 六引擎 × 四负载 × 四接口，共 96 组逐字符、逐字节核验，包含中文、emoji、原始 `<&>` |
| 对照依赖 | jte 3.2.5、JMustache 1.16、Mustache.java 0.9.14、FreeMarker 2.3.31、Pebble 3.2.2 |
| 首次创建 | 已启动并预热的 JVM，每次新建引擎或模板并输出 String，单次模式预热 1 次、测量 3 次、2 个 fork |
| 分配量 | 正式热渲染使用 JMH `gc` profiler，记录 `gc.alloc.rate.norm` |

`native` 使用各引擎默认 String 入口，`string` 使用初始容量 4096。
`writer` 创建容量 4096 的 StringWriter 并完成输出，计时返回 Writer 本身。
`utf8` 返回独占的完整 byte[]，Meepo 直接调用字节输出 API，jte 使用 binaryStaticContent，其他引擎先生成完整 String 再编码。
Meepo 字节收集容量为 4096 字节，jte 的 512 个 chunk 槽位采用其原有默认设计。

静态负载重复 64 行固定文本，占位负载包含姓名变换和数字输出，行负载分别处理 20 与 200 行。
大小写变换和真假判断在渲染期间执行，Mustache section 的真假判断可能分别调用谓词。
静态模板的 Meepo String 入口可以命中完整不可变结果缓存，Writer 与字节接口执行实际输出。

### 数据方向、相对指数与排名

每组 Mean ops/s 取两个 JVM 均值的算术平均，JVM means min–max 表示两个 JVM 均值的范围。

| 数据 | 含义 | 读数方向 |
|:--|:--|:--|
| Mean ops/s | 每秒完成的渲染次数 | 越高越好 |
| B/op | 每次渲染分配的字节数 | 越低越好 |
| Mean ms/op | 每次模板创建并首次输出的毫秒数 | 越低越好 |
| 多线程扩展倍数 | 当前线程数的总吞吐量除以 1 线程吞吐量 | 同一负载下越高越好 |
| 线程效率 | 扩展倍数除以线程数 | 同一线程数、负载下越高越好 |
| JVM means min–max | 两个 JVM 均值的最小值与最大值 | 用于观察跨 JVM 波动 |
| JFR 样本数与占比 | 指定采样周期与调用栈下的事件分布 | 用于定位热点 |

每个引擎对照表后增加相对表。每行限定同一负载、同一接口，以 Meepo 为 **100.0%**，相对指数统一为越高越好。

| 相对指数 | 计算公式 |
|:--|:--|
| 吞吐指数 | 其他引擎 ops/s ÷ Meepo ops/s × 100% |
| 分配效率指数 | Meepo B/op ÷ 其他引擎 B/op × 100% |
| 首次输出效率指数 | Meepo ms/op ÷ 其他引擎 ms/op × 100% |

单元格采用 `第 N · 指数（相对 Meepo 的差异）`，第 1 名的指数加粗。
例如 `第 1 · 144.3%（+44.3%）` 表示该项效率为 Meepo 的 1.443 倍，提高约 44.3%。
`80.0%（-20.0%）` 表示效率为 Meepo 的 80%，降低约 20%。
耗时或分配量减半时，相应效率指数为 `200.0%（+100.0%）`，原始耗时或分配量减少 50%。
耗时或分配量的效率指数为 80% 时，原始数值为 Meepo 的 125%，增加 25%。

排名按同一行的显示均值排序，相同数值并列。指数与差异保留 1 位小数，因此相同的显示指数可能对应不同名次。
百分比依据本页公布的均值换算，精度受原表舍入影响。Meepo 分配量显示为 0 B/op 的行，其他引擎的相对分配效率以 `—` 表示，名次按绝对分配量排序。
排名反映本次均值的观察顺序，接近结果应结合 JVM 均值范围理解。
不同接口、负载和缓冲容量采用各自口径解释。

### 结果分析

- 原生占位 String 入口的 Meepo 均值为 5,268,469 ops/s，分配为 1,184 B/op。固定容量 4096 的 String 入口为 1,300,402 ops/s、13,088 B/op，小结果对初始缓冲和 Unicode 扩容成本较敏感。
- 静态 String 负载主要执行完整结果缓存命中及 harness 分派。实际 Writer 输出为 1,300,773 ops/s，独占 UTF-8 数组输出为 3,227,471 ops/s，分别按相应输出契约衡量。
- 200 行负载中，Meepo 的原生 String 与 UTF-8 均值分别为 21,401、14,591 ops/s，jte 为 35,933、30,826 ops/s。JFR 的执行栈集中在 HashMap 查询、写入及执行上下文取引擎，分配样本包含 WHEN/ELSE 的捕获 lambda、执行映射节点和输出数组。
- Meepo 创建模板并首次输出的四组均值在 0.137–1.202 ms/op，jte 为 54.676–62.255 ms/op。jte 此路径包含 Java 模板编译，其热渲染结果体现编译后的执行路径。
- 共享模板在 8 线程下的总吞吐扩展为 1.70–3.83 倍，线程效率为 21.3%–47.9%。结果包含每次渲染的上下文、输出缓冲、编码及 GC 成本。
- 共享模板的 200 行 UTF-8 在 8 线程下扩展 3.83 倍，B/op 在 1、2、4、8 线程均为 72,816。交替字符集扩展 1.70 倍，B/op 从 147,353 增至 219,574，增长约 49.0%。
- 交替字符集的 8 线程分配采样中，Utxt.getBytes 占采样权重约 49.2%，可见 Encoded、SoftReference 与字符、字节缓冲。单项编码快照在并行交替字符集时反复重建。单线程交替输出还包含 GBK 与 UTF-8 自身的编码差异，分配变化应结合这两个因素解释。
- 缓存命中还受模板布局与线程调度影响。占位 mixed 的 B/op 从单线程 5,420 降至 8 线程 5,195，行循环场景则随线程数增加。共享正确性测试同时验证不同字符集并发输出的字节一致性。
- 各次 merge 创建独立 Acid，变量、引擎映射和分支胜出状态分别管理，可变引擎通过 fork 隔离。共享 Utxt 以完整快照发布编码，允许重复计算。自定义函数、模型对象和输入游标的并发使用遵循各自契约。
- 12 个单线程组合的两个 JVM 均值相差超过 15%，范围已逐项列出。例如 writer/rows20 的 Meepo 与 JMustache 均值相差不到 0.1%，接近结果应结合范围理解。
